# Windowseven MD — Payment Contract & Architecture

This document defines the payment integration architecture, transaction identity standards, server-side validation rules, and webhook processing semantics for Windowseven MD.

---

## 1. Decoupled Payment Architecture

Payment provider implementation details must never leak into controllers, the customer dashboard, subscription logic, or database repositories.

### Structural Flow
```text
Customer UI (Dashboard / Checkout)
            ↓
CustomerPurchaseService (Application Use-Case)
            ↓
PaymentService (Core Payment Lifecycle Domain)
            ↓
PaymentGateway (Provider-Agnostic Interface)
            ↓
FastLipaAdapter (Provider Implementation)
            ↓
FastLipa Payment Gateway / Mobile Operator
```

### Responsibility Matrix
* **CustomerPurchaseService**: Enforces customer authorization, tenant ownership, and plan selection.
* **PaymentService**: Manages the lifecycle of payment records in PostgreSQL (`PENDING` → `SUCCESS` / `FAILED`), enforces transaction idempotency, and coordinates subscription activation.
* **PaymentGateway (Interface)**: Defines normalized contracts for initiating transactions, verifying callbacks, and querying status.
* **FastLipaAdapter**: Translates Windowseven requests into FastLipa-specific formats, maps provider responses, and validates provider signatures.

## 2. Server-Authoritative Pricing Rules

The frontend client is strictly treated as untrusted.

1. **Client Submission Contract**:
   * The client submits only:
     ```json
     {
       "planId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
       "customerPhone": "255766183998"
     }
     ```
2. **Server-Side Resolution**:
   * The backend loads the plan directly from PostgreSQL:
     ```javascript
     const plan = await planRepo.findById(planId);
     if (!plan || plan.status !== 'ACTIVE') throw ApiError.badRequest('Invalid or inactive plan');
     ```
   * The payment record is created using:
     * `amount = plan.price`
     * `currency = plan.currency`
     * `durationDays = plan.duration_days`
3. **Rejection of Client Overrides**:
   * Any client-provided `amount`, `currency`, or `durationDays` is strictly ignored and discarded.

## 3. Transaction Identity & Safe Provider References

### 1. Internal Authoritative Identity
* Every payment is identified internally by a primary key UUID generated by PostgreSQL (`payments.id`).
* This UUID is the immutable single source of truth across all Windowseven services.

### 2. Provider-Facing Reference Standard
* External payment providers (like FastLipa) often require human-readable, URL-safe, alphanumeric transaction references.
* **Standard Format**: A safe, non-enumerable reference derived from the payment identity:
  ```text
  WS-<short-uuid-or-crypto-token>
  ```
  *(Example: `WS-B4F1A93C8D` or `WS-7D2E5F9A`)*
* **Rules**:
  * References must map **1:1 deterministically** to exactly one payment record in PostgreSQL (`payments.transaction_reference`).
  * Never use customer phone numbers, emails, tenant IDs, or sequential numbers as the transaction reference.
  * Timestamps are not mandatory in the reference.

## 4. Payment Activation & Webhook Verification

A subscription is activated **only** when a payment transition to `SUCCESS` is fully verified.

### 1. Verification Requirements
Before transitioning any payment to `SUCCESS` and activating a subscription, Windowseven validates:
1. **Webhook Authenticity**: The incoming callback matches the provider's cryptographic signature or shared secret.
2. **Internal Reference Matching**: The transaction reference matches an existing `PENDING` payment row in PostgreSQL.
3. **Tenant & Customer Ownership**: The payment belongs to the verified tenant context.
4. **Authoritative Plan Verification**: The plan referenced in the payment is valid and active.
5. **Amount & Currency Precision**: The provider-settled amount matches the authoritative database plan price (`provider.amount == payment.amount` and `provider.currency == payment.currency`).
6. **Provider Status**: The provider explicitly confirms a terminal success outcome (`SUCCESS` / `COMPLETED`).

### 2. Strict Webhook Idempotency (Replay Defense)
Payment webhooks are frequently retried by providers over unreliable networks. Windowseven guarantees **zero duplicate subscriptions**:

```sql
SELECT id, status, subscription_id 
FROM payments 
WHERE transaction_reference = $1 
FOR UPDATE;
```

* **If already `SUCCESS`**:
  * The handler detects `payment.status === 'SUCCESS'` and `payment.subscription_id IS NOT NULL`.
  * The webhook returns HTTP `200 OK` `{ status: 'ALREADY_PROCESSED' }` immediately.
  * **Zero database mutations occur**: No new subscription is created, and the expiration date is never extended a second time.
* **If in `PENDING`**:
  * The handler creates or extends the customer subscription inside the transaction.
  * Atomically updates `payments.status = 'SUCCESS'` and assigns `payments.subscription_id`.
  * Commits the transaction.

## 5. Distinction Between Payment Success and Merchant Settlement

In SaaS operations in Tanzania, mobile money collections and merchant withdrawals operate on different timelines:

```text
Customer Payment
       ↓
Mobile Money Deducted (M-Pesa / Tigo / Airtel)
       ↓
FastLipa Confirms SUCCESS
       ↓
[Windowseven Immediately Activates Subscription]  ← Real-Time Customer Activation
       ↓
FastLipa Merchant Balance Updated
       ↓
Merchant Withdrawal to Bank Account (T+1 or Manual Batch)
```

* **Authoritative Policy**:
  * Windowseven activates the customer's subscription **immediately** upon verified confirmation of customer payment (`SUCCESS`).
  * Windowseven **does not** delay customer access until merchant bank settlement clears.
  * Merchant withdrawal reconciliation is an internal accounting process separate from customer service provisioning.
